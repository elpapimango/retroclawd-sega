# CLAUDE.md

Guidance for Claude Code working in this repository.

## What this is

The Sega family of [retroclawd](https://github.com/elpapimango/retroclawd), a submodule of the application at
`machines/sega`: the Mega Drive / Genesis (`genesis`) as the machine plugin `sega_machine_plugin` (ids `genesis` and `segacd`). The design is
`docs/superpowers/specs/2026-10-24-sega-genesis-design.md` and the plan `docs/superpowers/plans/2026-10-24-sega-genesis.md`,
both in the application repository: read them first.

Rules that apply to every change:
- **No hardware fact from memory.** Every fact in code has a row in `docs/hardware-facts.md` labelled `[D]` datasheet, `[H]`
  documentation, `[O]` observed in reference emulators by a probe, `[H?]` unresolved, with its source. An I/O address
  without a fact stops the machine with a bounded report.
- Reference emulators (Genesis Plus GX, PicoDrive, BlastEm, clownmdemu; MAME) may be run and their source read for
  understanding. Copy no code, table, constant or comment; confirm each fact by a document or a probe on two oracles.
- Machine time comes only from the scheduler (`u64` master clocks); no wall clock, no floats in timing.
- `#![forbid(unsafe_code)]` in every Core, Chip and Machine crate; ROMs, states and firmware are untrusted input.
- Never commit ROMs, firmware (`bios_MD.bin`, `sk.bin`, ...), goldens, documents or oracle cores.

## Save states of the Mega-CD (2026-10-30)

`Expansion::save_state` / `load_state(bytes, now)` (default: none) let an expansion keep its own state; the Genesis `RCST` payload (schema 3) carries
it as `expansion: Option<Vec<u8>>`, and a state with a Mega-CD loads only into a Mega-CD machine (`OtherExpansion`) and the reverse. `SegaCdExp`
saves the sub-CPU, program/word/backup RAM, the gate array (with the CDC buffer and the CDD registers), the PCM chip, the graphics unit, the clocks
and the two audio resamplers (`SavedExp`, bincode); it names the BIOS by CRC and the region by the master clock and refuses another. The disc is
not in it: the drive saves only its position and mode (`Drive::state`/`restore`, `DiscDrive` states carry a CRC of the track table so another disc
is refused), and the disc is opened again from its file. Loading is atomic (the gate array goes first, it is the one part that can still refuse) and
every value is validated (`validate` on the CD chips; a flipped-byte sweep in `segacd` tests never panics). The backup RAM is part of the state
(loading a state also loads that backup RAM). Proof: unit tests (round trip, refusals, damage, whole machine) and the ignored
`a_saved_state_resumes_the_real_bios_and_disc_exactly` (`RC_BIOS`, `RC_DISC`, `RC_FRAMES`): Dragon's Lair at 600 and 1500 frames, Silpheed, Lunar,
both machines' states and pictures equal 120 frames after the load.

## CHD discs (2026-10-30)

`crates/formats/chd` reads CHD version 5 files from untrusted input (`forbid(unsafe_code)`; deps `flate2` miniz, `lzma-rust2` without its unsafe
`optimization` feature, `claxon`). Written from the documented layout (header comments of MAME's `chd.h`; the map, Huffman and codec framing
read in `chd.cpp`/`chdcodec.cpp`/`huffman.cpp`, the sector layout in `cdrom.cpp` and ECMA-130) with no code taken: the compressed map (type
codes, RLE of types, canonical Huffman of 16 symbols x 8 bits), the `cdzl`/`cdlz`/`cdfl` hunk framing (flag bit per frame for removed
sync and parity, length of the base run, deflate subcode), the P/Q parity regenerated by GF(2^8) arithmetic (poly 0x11D, the Horner and XOR sums;
the codec's tables turned out to be multiplication by the generator and by 1/(generator+1)), track metadata `CHT2`/`CHTR`, padding of tracks to
four frames. Audio is big-endian in the file (all three codecs) and `disc` turns it round. Not read by the CD view: GD-ROM, parent files, versions below 5; each says so (the generic `Image` reads parents and all codecs incl. `cdzs`). Proof: 14 unit tests (a built two-track file, damage at every byte, refusals), the `disc` tests, and
`crates/formats/chd/tests/real.rs` (ignored, `RC_CHD`): all 33 000 hunks of Mad Dog McCree (cdlz data, audio, subcode, regenerated ECC) hash to
the SHA-1 stored in the file's header, and the game boots from `--disc romm:6986` through the BIOS to its FMV. In a `.chd` track description
(a pregap type starting with `V` means the pregap's sectors are stored in the track's frames and the disc keeps them as the start of its data; any other type, as chdman writes for a cue `PREGAP`, means silence the disc makes up; checked against chdman 0.289 on both kinds).

## The CHD library (2026-10-30)

`crates/formats/chd` is a general CHD version 5 library, not only the CD reader the emulator uses. Layers: `codec.rs` (the nine hunk codecs both
ways: `zlib` raw deflate, `zstd` one Zstandard frame by the pure-Rust `ruzstd`, `lzma` raw LZMA lc3 lp0 pb2 by `lzma-rust2`, `huff` (`huff.rs`: canonical
Huffman of 256 byte symbols, tree in two stages), `flac` (`flac.rs`: our own encoder of bare frames, `L`/`B` byte-order marker), and `cd.rs` for
`cdzl`/`cdzs`/`cdlz`/`cdfl`), `image.rs` (`Image`: header, compressed and plain maps, metadata, parent files, `verify`), `chd`'s `Chd` (the CD view,
now built on `Image`), `writer.rs` (`Writer`: parallel hunk compression, best codec per hunk, repeated hunks and hunks the parent holds as references,
`mapenc.rs` for the compressed map, metadata chain, raw and overall SHA-1; uncompressed files are written the way chdman writes them, byte for byte),
`edit.rs` (add, replace and delete metadata in place, `write_hashes`). The tool on top is `rcchd` in `retroclawd-tools`. chdman 0.289 is the oracle
(`tests/chdman.rs`, `RC_CHDMAN=path cargo test -p chd --test chdman -- --ignored`): its files of every codec read and verify here, ours pass `chdman verify`
with the same SHA-1s. **A pregap type starting with `V` means the pregap's frames are stored in the track (cue `INDEX 00`); any other type (chdman writes
`MODE1` for a cue `PREGAP`) means silence.** The first version of the reader had this the other way round (found with chdman on both kinds of cue); audio
tracks of real CHDs were positioned two seconds off.

## Final Fight CD, what is known (2026-10-30)

Black screen, not solved. Established with `crates/machines/segacd/tests/bios.rs` (ignored probes: `where_are_both_cpus`, `registers_where_the_sub_cpu_reaches_an_address`
with `RC_STOP`, `which_routines_are_alive`, `main_side_at_the_stall`, `grep_the_bios_listing` with `RC_LIVE_DISC` to disassemble the live program RAM; the
sub-CPU I/O log takes `RC_IOFILTER`, `RC_IOSKIP`, `RC_IOMAX`):
- **Not the disc image:** the full 448 MB disc from RomM behaves like the truncated copy. **Not the CHD/PCM path:** the BIOS DMAs to program RAM (destination 5, 265 times) and word RAM (7), never PCM.
- **The reads work:** the BIOS reads 152 consecutive sectors in one burst (00:51:36 to 00:53:37, headers and modes right, 409 sectors of CDC interrupts in all), identical register traffic to the discs that boot, then stops by itself.
- **The wait:** both CPUs are alive. The sub-CPU runs the game's own program (not the BIOS) from `$6000`: a dispatcher at `$61C8` jumps through a table on the mode word at `$9B52`; mode 4 is the loop at `$8578` that ends when `$9B54` becomes non-zero, which only
  the mode-setting routine at `$6202` does (`st 2(a6)`). The mode changes when the sub's level-2 handler (`$88(a6)`, command from the main CPU) runs. The main CPU, in the game's IP in work RAM, has just called the BIOS user call 3
  (`moveq #8,d0 / jmp $35C`) and waits at `$FFFF103C` for `$8E65`, which its own level-2 handler sets when the sub raises IRQ2. The main side keeps sending (every 4 frames) command words that are all zero with IFL2 and flag toggles;
  the sub keeps answering with status `0101 0052 0050 0100`. So each side waits for the other's first real message.
- The BIOS's software error-check routine (`$4E74`/`$4FE2`, bits 5 and 6 of `$5BC2(a5)`, `addq.w #1,2(a6)`) is never reached and is not the setter of that flag (an earlier note said it was).
- Open question: what the main CPU is supposed to send after USERCALL3 (the main BIOS code at `$1800` stores `d0/d1` in `$FDE4/$FDE6` and sets main flag bit 2 only when `d0 = 1`), and whether the user-call data reaches the comm registers
  (they stay zero). Compare with Genesis Plus GX at the gate-array register level (it cannot be traced from outside; a patched build or its source is the way).

## Boot sweep of ten discs (2026-10-30)

Ten US discs from RomM (cue and bin pairs fetched into `software/discs/`), 2400 frames each from the real BIOS, picture compared with Genesis Plus GX at the
same frame (`discsweep.py` style: `retroclawd segacd --disc X.cue --firmware auto --headless --frames 2400 --dump-screen`):
- **Boot to their own screen or the BIOS one like GPGX:** After Burner III, Ecco the Dolphin, Flashback (mean difference 1.96 from GPGX), Silpheed, Dragon's Lair;
  Shining Force CD and Lunar reach the backup RAM prompt.
- **Black, GPGX shows a picture:** Final Fight CD (the map screen), Eternal Champions (GPGX: the backup RAM warning), Snatcher (GPGX: the "CD Backup RAM Cart SET" prompt).
  Snatcher has the same shape as Final Fight CD: the main CPU idles in `bra.s *` after testing its command byte `$A1201F` and the sub-CPU polls `tst.b $FF802F` (the
  main side's command byte 15); Eternal Champions has the main CPU waiting for status word 0 (`cmpi.w #0,$A12020`) while the sub-CPU spins at `$C61E`. So the Final Fight
  stall is not a one-game quirk: three of ten discs fail at the main/sub hand-over, which makes a trace against GPGX at the gate-array register level worth doing.
- **Earthworm Jim: Special Edition stops** with "sub-CPU read word $FF800A (pc $00711A): no fact covers this address": `$FF800A` is the CDC DMA address register, which fact E9 calls write only;
  the game reads it, so what a read returns (GPGX runs the game) is a fact still to find with a probe.

## Scenario manifest of the Mega-CD (2026-10-30)

`segacd.manifest.toml` (run by `rc-scenarios` like `genesis.manifest.toml`; BIOS `us_scd2_9306.bin` in `roms/segacd/`, discs in `software/discs/`, none committed) has S1 (the BIOS start-up animation at frames
300 and 600 and the "press start" screen at 900), S3 (Dragon's Lair, Silpheed and Lunar at frame 1200), S5 (save state determinism and reload, which the CD state work made possible) and S6 (frame length 896040 master clocks),
all passing, and S4 as a known gap. The pictures are Genesis Plus GX's, made by `scenarios/capture_segacd_goldens.py` (which prints the pins); `similarity` thresholds are the colour-level conversion (3.0 and 2.7 on the animation, 0.13 to 0.35 on
the later screens). S4: an audio-only disc (`scenarios/make_tone_disc.py`) reaches the BIOS CD player in both emulators but neither plays it unprompted, and none of Start, A, B, C and the d-pad started a track in Genesis Plus GX, so there is
no CD-DA tone to measure; the one manual comparison is fact E17. Not covered: S2 (the BIOS needs button sequences nobody has worked out), games past their loading, Final Fight CD.
